173: Source Code:
174: using System;
176: class MyStack<T>
177: {
178: private T[] items = new T[100];
179: private int top = -1;
181: public void Push(T item)
182: {
183: if (top == items.Length - 1)
184: {
185: Console.WriteLine("Stack Overflow");
186: return;
187: }
188: items[++top] = item;
189: }
191: public T Pop()
192: {
193: if (top == -1)
194: {
195: Console.WriteLine("Stack Underflow");
196: return default(T)!;
197: }
198: return items[top--];
199: }
201: public T Peek()
202: {
203: if (top == -1)
204: {
205: Console.WriteLine("Stack is empty");
206: return default(T)!;
207: }
208: return items[top];
209: }
210: }

216: MyStack<int> intStack = new MyStack<int>();

614: Purpose of Program.cs:
615: Program.cs is the entry point of the application. In .NET 6 and later it uses top-level statements and the minimal hosting model.
616: WebApplication.CreateBuilder(args) creates the host, loads configuration (appsettings.json, environment variables), logging and the dependency-injection container.
617: builder.Services.AddControllersWithViews() registers MVC services (controllers, Razor views, model binding, validation).
618: builder.Build() creates the app; the Use... calls add middleware to the HTTP request pipeline (exception handling, HTTPS redirection, static files, routing, authorization).
619: MapControllerRoute defines the default route {controller=Home}/{action=Index}/{id?}, and app.Run() starts the Kestrel web server.
620: Startup Configuration:
621: In .NET Core 3.1 / .NET 5 the configuration lived in a separate Startup class with two methods: ConfigureServices() to register services and Configure() to build the middleware pipeline.
622: From .NET 6 onwards both parts are merged into Program.cs: code before builder.Build() is the old ConfigureServices, and code after it is the old Configure method.

624: Controllers - classes that handle requests and return responses (HomeController).
625: Models - classes that represent data and business logic (ErrorViewModel).
626: Views - Razor (.cshtml) files; Shared contains the _Layout master page and partial views; _ViewStart sets the layout; _ViewImports holds common using statements and Tag Helpers.
627: wwwroot - static files (CSS, JavaScript, images, Bootstrap and jQuery libraries).
628: Properties/launchSettings.json - port numbers and environment used when running locally.
629: appsettings.json - application configuration such as connection strings and logging.

1752: using var cmd = new SqliteCommand(sql, conn);
1753: cmd.Parameters.AddWithValue("@username", username); // parameter, not string-concatenated
1755: using var reader = cmd.ExecuteReader();
1757: var rows = new List<string>();
1758: while (reader.Read())

1766: Sample Output
1767: 1) VULNERABLE (string concatenation)
1768: SQL: SELECT COUNT(*) FROM Users WHERE Username = 'admin'
1769: AND Password = '' OR '1'='1'
1770: Login SUCCESS - HACKED!
1772: 2) SAFE (parameterized query)
1773: SQL: SELECT COUNT(*) FROM Users WHERE Username = @user AND Password = @pass
1774: Login FAILED - attack blocked
1776: 3) SAFE login with correct password
1777: Login SUCCESS
1779: Explanation of the Difference:
1780: Vulnerable query: user input is joined directly into the SQL string. The input ' OR '1'='1 closes the quote and adds OR '1'='1', which is always true, so the WHERE clause matches every row and login succeeds without the real password.
1781: Parameterized query: the SQL text contains placeholders (@user, @pass). The command text and the values are sent separately to the database, so the input is always treated as plain data, never as SQL code. The attacker's string is simply compared as a password and fails.
1782: Entity Framework Core: LINQ queries (and FromSqlInterpolated) automatically generate parameterized SQL, so they are protected against SQL Injection by default.
1783: Rule: never build SQL by concatenating user input; always use parameters, stored procedures with parameters, or an ORM like EF Core, and also validate input.
